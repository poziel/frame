# TypeScript and JavaScript

Use the [Google TypeScript Style Guide](https://google.github.io/styleguide/tsguide.html)
as the baseline. The explicit project rules below override its formatting
conventions where they differ. The same syntax conventions apply to JavaScript
and to scripts inside Vue components.

## Classes and files

Use classes for live framework objects that own state, behavior, subscriptions,
or lifecycle. Put behavior on the owning item; registry convenience methods
delegate to that item. Keep state isolated to the owning Frame instance.

Use one class per file, following the existing filename convention in its
folder. Small supporting interfaces, types, and enums may stay beside their
owning class. Independently owned classes get their own files. Re-export entry
points can preserve public import paths without collecting implementations.

Pure functions and data-only interfaces do not need artificial class wrappers.
Do not introduce classes containing only static methods for namespacing.

Inside a class, put properties first, then the constructor, then methods.
Prefer public operations before protected extension points and private helpers.
Do not reorder existing executable property initializers automatically: their
evaluation order can affect behavior. Use ordinary methods; retain bound
callbacks when an API intentionally passes them around independently.

## TSDoc

Document every class, constructor, property, and method, including private
members. Document associated interface members when they define a consumer
contract. Attach `/** ... */` comments directly to their declarations so editor
hovers, autocomplete, and emitted declarations can expose them.

Explain purpose and behavior rather than repeating the identifier. Give complex
classes a multiline explanation and a small `@example` where useful. Keep simple
types concise. Use `@param name - description`, `@typeParam`, `@returns`,
`@remarks`, and `@throws` when they add useful contract information. Do not
duplicate TypeScript types in documentation or add meaningless `@returns void`.

```ts
/** Owns a contextual permission and its manual override lifecycle. */
export class Permission {

  /** Stable identifier within the owning registry. */
  readonly id: string;

  /**
   * Creates an independently owned permission.
   *
   * @param id - Unique identifier used by the host application.
   */
  constructor(id: string) {
    this.id = id;
  }

  /**
   * Removes a temporary override and resumes automatic evaluation.
   *
   * @remarks
   * Independent feature and command restrictions remain authoritative.
   */
  reset(): void {
    // Delegate to the permission's automatic-state implementation.
  }
}
```

This example illustrates code style, not a replacement definition of Frame's
public Permission API.

## Spacing

Leave one blank line after the opening brace of a nonempty class or interface,
and one blank line between distinct members. Keep each member's TSDoc attached
to that member. Do not add a blank line before the closing brace. Separate
imports from following declarations, and separate distinct type/class
declarations with a blank line.

```ts
import type {PermissionSource} from './permission';

/** Registration data owned by one permission. */
export interface PermissionOptions {

  /** Unique registration identifier. */
  id: string;

  /** Automatic condition or reactive source. */
  allowed: PermissionSource<boolean, void>;
}
```

## Parameters

Definitions with six or fewer parameters stay on one line when the complete
signature fits 80 columns. More than six parameters, or a longer signature,
puts each parameter on its own line. Preserve comments and structurally
multiline parameter types/defaults in vertical layouts. This applies to
constructors, functions, methods, callbacks, and callable type signatures;
function-call arguments use the baseline formatter's layout.

```ts
function openView(id: string, focus: boolean): void {}

function configure(
  first: string,
  second: string,
  third: string,
  fourth: string,
  fifth: string,
  sixth: string,
  seventh: string
): void {}
```

## Remaining baseline

Use single-quoted strings, semicolons, named exports, explicit visibility for
private members, and `readonly` where ownership permits. Do not use `any` to
avoid modeling a contract; use `unknown` with narrowing. Prefer explicit
interfaces and discriminated unions for public structured data. Use type-only
imports for type dependencies. Vue SFC default exports generated by the
component compiler are an exception to the named-export convention.
